# User Migration Rollback Approach

## Purpose

This document defines the rollback approach for the User Migration Service.

The service migrates data from:

- `users.csv`
- `beneficiaries.csv`
- `templates.csv`

The service can also process batch-wise input files automatically when the CSV folder contains matching numbered sets, for example:

- `users_1.csv`, `beneficiaries_1.csv`, `templates_1.csv`
- `users_2.csv`, `beneficiaries_2.csv`, `templates_2.csv`

into:

- `pending_user`
- `migrate_beneficiary`
- `migrate_template`

## Rollback Scope

There are two rollback scenarios:

1. Automatic rollback during DB execution failure
2. Manual rollback after DB execution has already committed

## 1. Automatic Rollback During Execution Failure

When the migration API is called with:

```text
executeToDb=true
```

the database insert execution runs inside one Spring transaction.

Current implementation:

```java
@Transactional
public SqlExecutionResult executeGeneratedSql(...)
```

For batch-wise files, each discovered batch is generated and executed separately by the endpoint. This means `batch-1` and `batch-2` have separate DB execution calls and separate transaction boundaries.

### Behavior

If all DB insert statements complete successfully:

- Spring commits the transaction at the end of DB execution.
- The API returns success.

If any runtime error occurs during DB execution:

- Spring rolls back the database transaction.
- Inserted rows from that failed execution are not committed.
- The API returns `500 Database execution failed`.
- Failure details are written to application and batch logs.

For batch-wise execution:

- If `batch-1` commits successfully and `batch-2` fails later, `batch-1` is not automatically rolled back with `batch-2`.
- The failed batch is rolled back automatically by its own transaction.
- Any earlier committed batch must be rolled back manually if the business decision is to reverse the full migration run.

### Important Notes

`ON CONFLICT DO NOTHING` does not cause rollback.

Those rows are treated as conflict-skipped rows, not failed rows. The transaction can still commit.

### What Is Rolled Back Automatically

- Inserts into `pending_user`
- Inserts into `migrate_beneficiary`
- Inserts into `migrate_template`

### What Is Not Rolled Back Automatically

The following files/logs are written outside the DB transaction and are not automatically removed:

- generated SQL file
- fail summary file
- migration data CSV
- application log
- batch log
- success CSV files, if already written

## 2. Manual Rollback After Successful Commit

If the migration completes and commits successfully, rollback must be performed manually by the DB / Server Team.

The recommended rollback source is the successful migration CSV output generated by the service.

After DB execution, the service creates successful migration files such as:

```text
migration_success_<timestamp>_users.csv
migration_success_<timestamp>_beneficiaries.csv
migration_success_<timestamp>_templates.csv
```

For batch-wise execution, the batch ID is included in the success file name:

```text
migration_success_batch-1_<timestamp>_users.csv
migration_success_batch-1_<timestamp>_beneficiaries.csv
migration_success_batch-1_<timestamp>_templates.csv

migration_success_batch-2_<timestamp>_users.csv
migration_success_batch-2_<timestamp>_beneficiaries.csv
migration_success_batch-2_<timestamp>_templates.csv
```

These files contain only rows that were successfully inserted into the database.

## Manual Rollback Strategy

Use the success CSV files to identify exactly which rows were inserted.

Rollback must be executed in this order:

1. Delete templates from `migrate_template`
2. Delete beneficiaries from `migrate_beneficiary`
3. Delete users from `pending_user`

This order avoids leaving child/migration records behind after user records are removed.

## Rollback Matching Rules

### `migrate_template`

Match by:

- `cif`
- `template_name`

Additional safe filters can be added where available:

- `to_account`
- `recipient_bank`
- `transfer_type`

### `migrate_beneficiary`

Match by:

- `cif`
- `account_number`
- `nickname`
- `type`

### `pending_user`

Match by:

- `migrate_user = true`
- `cif`
- `username`

Additional safe filters can be added where available:

- `migrated_username`
- `fda_account_created_date_time`
- `fda_account_status`
- `fda_account_remarks`
- `number_of_otp_attempts`
- `number_of_login_attempts`
- `mobile`
- `email`
- `identity_number`

## Recommended Manual Rollback Steps

1. Stop new migration execution for the same data set.
2. Identify the migration batch ID, timestamp, and request ID from logs.
3. Locate the generated successful migration CSV files for the exact batch or batches being rolled back.
4. Take a database backup or snapshot before manual rollback.
5. Load the successful CSV files into temporary rollback staging tables.
6. Run the rollback SQL inside a transaction.
7. Verify row counts before commit.
8. Commit only after the DB / Server Team confirms the deleted rows are correct.
9. Keep the rollback SQL output and logs as audit evidence.

## Rollback Transaction Pattern

Use this transaction pattern:

```sql
BEGIN;

-- 1. Run DELETE statements.
-- 2. Review affected row counts.
-- 3. Verify remaining data.

-- If correct:
COMMIT;

-- If not correct:
-- ROLLBACK;
```

## Verification Queries

Before rollback, count matching records:

```sql
SELECT COUNT(*)
FROM migrate_template mt
JOIN rollback_templates rt
  ON rt.cif = mt.cif
 AND rt.template_name = mt.template_name;

SELECT COUNT(*)
FROM migrate_beneficiary mb
JOIN rollback_beneficiaries rb
  ON rb.cif = mb.cif
 AND rb.account_number = mb.account_number
 AND rb.nickname = mb.nickname;

SELECT COUNT(*)
FROM pending_user pu
JOIN rollback_users ru
  ON ru.cif = pu.cif
 AND UPPER(ru.username) = UPPER(pu.username)
WHERE pu.migrate_user = true;
```

After rollback, the same counts should be `0` for the rolled-back batch.

For the new migration columns, optional verification can be added when the successful users CSV contains the values:

```sql
SELECT COUNT(*)
FROM pending_user pu
JOIN rollback_users ru
  ON ru.cif = pu.cif
 AND UPPER(ru.username) = UPPER(pu.username)
 AND UPPER(COALESCE(ru.username, '')) = UPPER(COALESCE(pu.migrated_username, ''))
WHERE pu.migrate_user = true;
```

The FDA account fields and attempt-count fields should be treated as audit/supporting filters, not the only match keys.

## Rollback Approval

Manual rollback should be approved by:

- DB / Server Team
- Application Owner
- Business / Bank Team, when production data is involved

## Sequence Diagram Note

The rollback path can be documented in the sequence diagram as:

```text
alt DB execution error before commit
  Migration Service -> Database: rollback transaction
  Migration Service -> Logs: write failure reason
  Migration Service -> DB / Server Team: HTTP 500 Database execution failed
end

alt rollback required after successful commit
  DB / Server Team -> Logs / Output: collect success CSV files
  DB / Server Team -> Database: run manual rollback SQL in transaction
  Database -> DB / Server Team: deleted row counts
  DB / Server Team -> Database: commit or rollback manual rollback transaction
end

alt batch-wise migration
  Migration Service -> CSV Folder: discover users_N, beneficiaries_N, templates_N groups
  loop each batch
    Migration Service -> Database: execute batch in its own transaction
    Migration Service -> Output / Logs: write batch-specific SQL, data, fail-summary, success CSV files
  end
end
```
